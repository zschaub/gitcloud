## [0.2.11] - Unreleased

### Fixed

- **Snapshot history was ordered non-deterministically** (Phase 3 `#GC-Phase3-Bug-1`, logged by the 2026-09-13 review). `SnapshotMapper::findAllForUser`, `findAllForFile`, and `findLatestForFileId` ordered rows only by `created_at`, a whole-second `bigint` (`Version000102Date20260704120000.php`; `ITimeFactory::getTime()`), so two snapshots recorded for the same file within the same second had no defined relative order — observed live as the rollback panel labelling an older snapshot "Current version" while offering the actually-newest one as a rollback target. The same ambiguous ordering fed the auto-commit listeners' "latest snapshot" gate (`findLatestForFileId`, used to decide whether a deleted/renamed/restored file has GitCloud history and what to chain a new snapshot's parent to) and the dashboard's Deleted-pill logic (`getLatestStatusByFilePath`, which trusts "first row seen for a path" from `findAllForUser`'s result order). A sibling method, `findAllForUserUnderPath`, already broke ties correctly with `->addOrderBy('id', 'DESC')` (added in 0.1.25 for an unrelated reason — scoping a folder-delete's tracked-descendant lookup to SQL) — the fix applies that exact same, already-precedented tiebreaker to the three methods that were missing it, since the table's auto-increment `id` primary key is guaranteed to follow insertion order (every insert goes through the single `QBMapper::insert()` call in `VcsService::createSnapshotRecord()`) and so never disagrees with `created_at` for two real rows, only resolves the case where `created_at` alone can't.
  - Verified end-to-end against the running `stable34` instance: committed two real snapshots for the same file (naturally landing 1 second apart), then directly forced both rows' `created_at` in the database to the identical value to reproduce the exact same-second collision described in the bug report. `GET /apps/gitcloud/snapshots` continued to correctly return the newer snapshot first (which `RollbackPanel.vue` labels "Current version") even with `created_at` tied, and a subsequent third commit correctly chained its `parentSnapshotId` to the newer of the two tied rows rather than the older one — confirming the fix for both the rollback panel and the auto-commit "latest snapshot" gate. Full PHPUnit suite (163 tests, 388 assertions — unchanged, since this is a pure ordering fix with no new branch) verified passing inside the running `stable34` container (synced via `docker cp` + a restart first); `composer lint` and `composer cs:check` also verified. No dedicated `SnapshotMapper` unit test suite exists in this codebase (there is no live-DB test convention here — every existing test mocks `SnapshotMapper` and hands its consumers pre-ordered arrays), so none was added for this one-line-per-method query change; the live-instance verification above stands in its place.
- **Renaming/moving or trash-restoring a tracked *folder* silently lost tracking of the files inside it** (Phase 3 `#GC-Phase3-Bug-2`, logged by the 2026-09-13 review). `GitTrackedNodeRenamedListener` and `GitTrackedNodeRestoredListener` each gated on `SnapshotMapper::findLatestForFileId($userId, $target->getId())` returning history for the event's own node - which a folder never has, only the files inside it do - so a renamed folder's files vanished from the dashboard entirely (not even tagged `Deleted`) and a restored folder's files stayed stuck at their last recorded `deleted` status in both GitCloud's bookkeeping and git's own index. `GitTrackedNodeDeletedListener` got exactly this fix for the delete case back in 0.1.25 (`autoCommitDeletedFolderDescendants`, added after empirically confirming Nextcloud's Files-app delete flow dispatches one event for a whole folder rather than one per descendant file, and that the event's node is a generic stand-in with no history of its own); the rename and restore listeners simply never received the same follow-up.
  - Both listeners now mirror that exact pattern: on their existing single-file gate missing, they fall through to a new private method (`autoCommitRenamedFolderDescendants`/`autoCommitRestoredFolderDescendants`) that treats the event's own path as a possible folder prefix, looks up every tracked descendant via the same `SnapshotMapper::findAllForUserUnderPath($userId, $prefix . '/')` the delete listener already uses (deduplicated to each file_id's latest snapshot, since results come back newest-first), and auto-commits each one individually - a rename computes each descendant's new path by substituting the old folder-path prefix for the new one (`NodeRenamedEvent::getSource()`, not previously used by this listener, supplies the old folder path; `getTarget()` the new one), while a restore restores only the descendants whose latest status is actually `deleted`, leaving anything already in sync untouched. The rename fallback also reuses the single-file case's existing `WorkingTree::contains()` check (against the folder's own new node, once, rather than per descendant) so a folder moved onto a different storage - a group folder, a received share - auto-commits a deletion of every descendant instead of a rename it has nowhere to stage, exactly like the single-file case already does. Both fallbacks are safe no-ops for an ordinary untracked folder, whose path never matches any tracked file's prefix. No `VcsService` or `SnapshotMapper` changes were needed - both fallbacks call the exact same `autoCommitRename`/`autoCommitDelete`/`autoCommitRestore` methods already used for the single-file case, once per descendant.
  - Verified end-to-end against the running `stable34` instance: created a real folder with two files, committed it, then moved the folder via a real WebDAV `MOVE` - both files correctly followed to the new path with `Unchanged` status (previously they would have vanished from the dashboard entirely), and one file's snapshot history shows a real `Auto-commit: renamed RenameTestFolder/one.txt to RenamedFolder/one.txt` entry chained to its prior commit. Deleting that same folder correctly tagged both files `Deleted` (the pre-existing 0.1.25 behavior, confirmed unaffected), and restoring it from the trash via a real DAV trashbin `MOVE` to the `restore/` collection brought both files back to `Unchanged` with their content intact on disk (confirmed via a WebDAV `GET`) - previously they would have stayed `Deleted` forever. Full PHPUnit suite (170 tests, up from 163, 406 assertions, up from 388) verified passing inside the running `stable34` container (synced via `docker cp` + a restart first); `composer lint` and `composer cs:check` also verified. Covered by 7 new listener test cases mirroring the delete listener's own 0.1.25 test conventions exactly: for rename, auto-committing a rename for each tracked descendant (skipping one already recorded `deleted`), only considering each file_id's latest snapshot, a no-op at the repository root, and recording a deletion for each descendant when the folder itself moves outside the working tree; for restore, auto-committing a restore for each descendant currently marked `deleted` (leaving an already-synced one alone), only considering each file_id's latest snapshot, and a no-op at the repository root. Two pre-existing "no history" tests in each listener's suite needed small updates to stub the now-always-exercised fallback path's own lookups (mirroring the equivalent update `GitTrackedNodeDeletedListenerTest` already needed in 0.1.25) rather than assuming an early return.
- **A failed static-git install still reported success** (Phase 3 `#GC-Phase3-Bug-5`, logged by the 2026-09-13 review). `GitStaticBinaryService::downloadForCurrentArchitecture()` called `copy()`, `chmod()`, and `file_put_contents()` (writing the binary itself, making it executable, and recording its `git.version` marker respectively) without checking any of their return values - all three fail by returning `false` and emitting a PHP warning rather than throwing, so on a read-only app directory the binary was silently never written (or written but never made executable, or installed with no version marker) while the method still fell through to its unconditional `['success' => true, ...]` at the end. An admin on a read-only install would see "Downloaded static git vX for Y." and a version number in the status list for a binary that doesn't actually exist on disk. All three calls now check their return value and return a clear `['success' => false, 'message' => ...]` immediately on failure, matching every other failure branch already in this method (checksum mismatch, extraction failure, unexpected archive layout, `mkdir` failure); each is `@`-suppressed and checked via its return value rather than the emitted warning, the same convention `runProcess()`'s own `@proc_open` in the same class already uses.
  - Covered by a new `testDownloadForCurrentArchitectureFailsWithClearMessageWhenBinDirectoryIsNotWritable`, which reproduces the read-only app directory scenario for real (`chmod 0500` on the target `bin/<arch>` directory before installing) and asserts the method now reports failure with neither the binary nor its version marker left on disk. This needed real, unprivileged filesystem permission enforcement to mean anything - run as the container's own root user (as this suite normally is per this project's convention), a `chmod`-based write block is a no-op and the test would misleadingly pass either way, so the new test defensively skips itself under `posix_getuid() === 0`. Confirmed the underlying fix actually works by additionally running this project's entire suite as `www-data` inside the container (`su -s /bin/sh www-data -c '...'`) rather than as root: **171 tests, 410 assertions, 0 skipped** (versus 171 tests but 1 skipped as root) - the new test only genuinely exercises the bug under a real unprivileged user, exactly the scenario (`www-data`/php-fpm on a read-only app directory) the bug report describes.
- **"Static git is already up to date" was shown even when the installed version is unknown** (Phase 3 `#GC-Phase3-Bug-6`, logged by the 2026-09-13 review) - e.g. a binary installed before 0.2.5's version-marker feature existed, or one whose marker file was later lost. The backend's `getStatus()` already correctly distinguished the two cases in its data (`installedVersion: null` for "unknown" versus a real version string for "known"), but `AdminSettings.vue`'s note card was keyed purely on `!gitStatus.updateAvailable`, which is `false` for both "genuinely up to date" and "unknown" - the template never branched on `installedVersion` at all. Split into two mutually exclusive `NcNoteCard`s: the existing green "already up to date" one now additionally requires `installedVersion !== null`, and a new amber one explains the version is unknown and that re-downloading will enable update checks. Since that message asks the admin to re-download, but the existing "Download static git" button was only ever shown while `!staticGitAvailable` (i.e. only before any binary exists), it also now shows whenever `installedVersion === null` regardless of `staticGitAvailable`, so the message's suggested action is actually reachable from the same screen instead of a dead end.
  - No backend or API response-shape change was needed - `installedVersion` was already present in `GET /apps/gitcloud/admin/git-binary-status`'s response. This project has no frontend component test framework (`find` confirms no `*.spec.ts`/`*.test.ts` files and no `vitest`/`jest` anywhere in `package.json`), so this is a template-only, backend-test-free fix; verified instead via `npm run lint`, `npm run stylelint`, and a clean `vite build`, plus a live check against the running `stable34` instance's real, already-installed amd64 static git binary: temporarily removed its real `git.version` marker (backed up first) and confirmed `GET /apps/gitcloud/admin/git-binary-status` returns exactly the `installedVersion: null, updateAvailable: false` payload the new template branch keys on, before immediately restoring the marker from the backup and re-confirming the endpoint reported the original `v2.55.0-1` again. Browser-level visual confirmation of the rendered note card was not possible in this session (no browser-automation tool available) - the user should confirm the amber "version unknown" note and re-enabled download button actually render correctly for this state.
- **The Files-app "Add to GitCloud" commit dialog rendered unstyled** (Phase 3 `#GC-Phase3-Bug-3`, logged by the 2026-09-13 review). `LoadAdditionalScriptsListener` registered the `gitcloud-files-actions` script via `Util::addScript()` but never called the matching `Util::addStyle()` - the stylesheet was built and sitting on disk (`css/gitcloud-files-actions.css`, correctly `@import`-ing `CommitDialog`'s own scoped chunk CSS) but never enqueued into the Files app page, so the dialog rendered with browser-default styling. Verified against the running `stable34` instance: `GET /apps/files/` now includes a `<link>` to `/apps-extra/gitcloud/css/gitcloud-files-actions.css` alongside the existing script tag, where before only the script was present.

Not independently re-measured pixel-for-pixel against a real browser this session (no browser-automation tool available) - the user should confirm the dashboard now matches the Files app's content width at the same viewport.

- **Dark-theme (and, it turns out, light-theme) contrast: several status pills and result lines used a background-only theme colour for text** (Phase 3 `#GC-Phase3-Bug-8`, logged by the 2026-09-13 review, describing the same pattern 0.2.3 already fixed for the dashboard's own success/error banners but explicitly left everywhere else). Nextcloud's theme defines colours like `--color-success`/`--color-error`/`--color-warning` as pale-tint-in-light/dark-tint-in-dark tones meant only for backgrounds, with separate `-text` variants (e.g. `--color-success-text`) calibrated to be readable against them - using the base variable for text instead reproduces 0.2.3's exact bug. Fixed six occurrences: `RollbackPanel.vue`'s success/error banners and success pill, `CommitDialog.vue`'s two result lines, and the dashboard's Overview "N modified" pill (`App.vue`).
  - While reading every remaining background-only-colour-as-text usage for this fix (rather than only the ones named in the bug report), two more were checked against this Nextcloud instance's *actual* computed theme CSS (`/apps/theming/theme/{light,dark}.css`) instead of guessed: `RollbackPanel.vue`'s "uncommitted" equivalent pill, `.directory-row__pill--uncommitted` in `App.vue`, uses `--color-primary-element` as text on a `--color-primary-element`-tinted background - this is a *legitimate* usage of that variable (unlike `--color-warning`/`--color-success`, `--color-primary-element` is itself a mid-saturation accent color designed to be used directly as text/icon color, confirmed contrast-safe against its own 15% tint in both themes by computing real light/dark hex values) and was deliberately left unchanged despite superficially matching the buggy pattern - swapping it to `--color-primary-element-text` (white in light theme, black in dark theme, meant for text *on a solid* `--color-primary-element` button) would have made it nearly invisible against its own pale tint background, a strictly worse regression. This computed-value verification is what caught that the two visually-similar cases needed opposite treatment, rather than mechanically applying one swap pattern everywhere.

#### The 2026-09-15 deep review's eleven bugs (`#GC-Phase3-Bug-10` … `-20`)

All eleven are fixed below. `#GC-Phase3-Maint-2` (the maintenance sweep logged alongside them) is deliberately **not** included and stays open.

- **(DATA LOSS) A filename containing a git pathspec glob character silently committed and rolled back *other* files** (`#GC-Phase3-Bug-10`). Every git invocation passed the Nextcloud-relative path as a bare pathspec after `--`, which stops *option* parsing but not *glob* matching - so a real file named `report-*.txt` (`*`, `?`, `[` and `]` are all legal Nextcloud filenames on Linux) was handed to git as a pattern and matched every sibling. Committing it also committed `report-private.txt` and `report-public.txt` while recording a snapshot row for only one of them, and rolling it back overwrote all three on disk, destroying uncommitted content that had never been committed anywhere. Fixed by prefixing every path with git's `:(literal)` pathspec magic, via two new private helpers (`literalPathspec()`/`literalPathspecs()`), at all six call sites that pass a path to git: `commitChanges`'s and `autoCommitChange`'s `git add`, `getDirectoryStatus`'s and `getFileStatuses`'s `git status --porcelain`, and `rollbackToSnapshot`'s `git checkout` and `git add`. Chosen over the `--pathspec-from-file=-` route the bug report also suggested, since `runProcess()` opens no stdin pipe today and would have needed one. Prefixing is safe for a path that itself starts with `:`, since git strips exactly one magic prefix.
- **"Stop tracking" was one-way - an untracked file could never be tracked again** (`#GC-Phase3-Bug-11`), and the same dead end stranded files from bugs 10, 12 and 14. `untrackFile()` deletes a file's snapshot rows and deliberately leaves git history alone (correct, and documented), but `commitChanges` decided there was nothing to do purely from `git diff --cached --quiet` - which is empty precisely *because* git still holds the content - and returned an error before reaching the snapshot-recording loop. The file sat as `Uncommitted` forever, with no UI path to recover, until its content happened to change. That branch now routes to a new `recordSnapshotsForAlreadyCommittedFiles()`: a file that git already tracks (checked with a single `git ls-files -z`, via a new `listPathsTrackedByGit()`) but that GitCloud has no history for is re-linked to the current `HEAD` with a fresh snapshot row, while a file GitCloud *does* still have history for genuinely has nothing to commit and keeps the original "No changes to commit for the selected file(s)." message. The history check uses both `findLatestForFileId` and an exact-path lookup, so legacy rows predating the `file_id` migration count as history exactly as they do in `untrackFile()` itself.
- **Concurrent commits collided on git's `index.lock`; most failed, and raw git output was dumped to the user** (`#GC-Phase3-Bug-12`). There was no locking anywhere in the codebase, so six parallel commits against one repository left only two survivors, and one failure pasted git's entire porcelain status - a listing of the user's unrelated untracked files - verbatim into the API response. Not a synthetic scenario: a sync client uploading several files fires several auto-commit listeners at once, which race the dashboard's own commits. Fixed with a new `withRepositoryLock()` that serializes per-user git access with an exclusive `flock()` held across the whole stage->commit->record sequence (not per git invocation - it is the sequence that has to be atomic), now wrapping `commitChanges`, `autoCommitChange`, `rollbackToSnapshot` and `deleteHistory`. The lock file is a sibling of the Git directory (`<data>/<user>/gitcloud.lock`) rather than a file inside it, so it survives `deleteHistory()` removing that directory underneath a waiter; no locked operation calls another, so nothing can self-deadlock. `acquireLock()` polls a non-blocking `flock()` for up to 10 seconds rather than blocking indefinitely, so a stuck holder produces a clear `REPOSITORY_BUSY_MESSAGE` ("Another GitCloud operation is still running on your files…") instead of a hung request; a lock file that can't be opened at all logs a warning and degrades to the previous unserialized behavior rather than blocking the user outright. Separately, a new `summariseGitOutput()` now condenses git's own output to its first 3 lines / 400 characters before it reaches an API response, while the full output is still logged untouched - applied to all nine user-facing `Failed to …: %s` messages across `commitChanges`, `autoCommitChange`, `ensureRepository`, `rollbackToSnapshot` and `createHistoryBackup`. `ILockingProvider` was considered and rejected: GitCloud is home-storage-only by construction (every path checks `isLocal()`), so the repository is always on a local filesystem where `flock()` is the right primitive, and it needs no constructor change across the suite's ~50 direct `new VcsService(...)` call sites.
- **(DATA LOSS) `deleteHistory` reported success after a partial wipe, leaving a corrupt repository that broke every future commit** (`#GC-Phase3-Bug-13`) - the same unchecked-return-value defect as the already-fixed `#GC-Phase3-Bug-5`, in a sibling method. `removeDirectoryRecursive()` ignored every `unlink()`/`rmdir()` return value including its own final `rmdir($path)`, so on a read-only data directory it emptied whatever it could reach (`objects/`, `refs/`) while `HEAD`, `config` and `index` survived; `hasRepository()`'s bare `is_dir()` still passed, so `ensureRepository()` short-circuited and never reinitialised, the snapshot rows were deleted anyway, and the user was left with no history, no rows, a broken repository (`error: Error building trees` on every later commit) and a green success message. Two changes: `removeDirectoryRecursive()` now checks every `unlink`/`rmdir` (each `@`-suppressed and checked via its return value, the same convention `runProcess()`'s own `@proc_open` uses) and returns whether everything was actually removed, with `deleteHistory` aborting on failure **before** `SnapshotMapper::deleteAllForUser` is reached; and a new `canRemoveDirectoryRecursive()` pre-flight refuses the wipe up front when any directory in the tree - or the Git directory's own parent - isn't writable, since deleting an entry needs write permission on the directory *containing* it. The pre-flight is what turns the reported scenario from "half-deleted repository" into a clean refusal with the history left intact; the return-value check is the backstop for everything it can't predict.
- **A commit message longer than 4000 characters returned HTTP 500, committed to git anyway, and stranded the file** (`#GC-Phase3-Bug-14`). `gitcloud_snapshots`.`message` is a 4000-character column but nothing bounded the message at the API boundary, so git committed successfully and the snapshot insert then threw `SQLSTATE[22001] Data too long` - leaving the file in git history with no row, i.e. permanently `Uncommitted` per bug 11 above. `ApiController::commitChanges` now rejects an over-long message with a 400 naming the limit before any git work happens, keyed on a new `VcsService::MAX_COMMIT_MESSAGE_LENGTH` constant documenting which migration the number comes from. As a second layer, `createSnapshotRecord()` truncates to the same limit: the messages GitCloud generates itself embed file paths and so have no fixed length either, and no insert should ever be able to throw after git has already committed.
- **A `..` path segment in any path parameter returned HTTP 500 instead of a clean 400** (`#GC-Phase3-Bug-15`). `ApiController` caught `NotFoundException` around `$userFolder->get()` but not the other half of that method's documented contract. No security impact - core blocks the traversal and nothing reaches git - but it logged an exception and returned an unhelpful OCS 996. Now caught alongside `NotFoundException` in `commitChanges` and `findUncommittedFiles`, and handled with its own branch in `getSnapshots` and `rollbackSnapshot`: those two deliberately fall back to a file's *last known path* when the live node is gone (so a deleted file keeps its History and Rollback), which a path core refuses outright can never be, so it gets the same "File not found" 400 instead.
  - The bug report named `OCP\Files\InvalidPathException` as the exception to catch; that is **wrong**, and catching it fixed nothing - the live instance kept returning 500. The exception core actually throws here is `OCP\Files\NotPermittedException`, raised by `Folder::getFullPath()`'s `isValidPath()` check and declared in `OCP\Files\Folder::get()`'s own `@throws` alongside `NotFoundException` (read from this instance's core source, and confirmed against `nextcloud.log`'s recorded exception class and stack trace, rather than taken from the report). Caught only once the fix was driven against the running instance - the unit tests passed either way, since they stub whichever exception the test itself throws.
- **(Accessibility) The committed-directories list was completely unreachable by keyboard** (`#GC-Phase3-Bug-16`). Each row was a bare `<li @click>` with no `role`, `tabindex` or key handler, and selecting a directory is the only route to Directory Detail - and so to commit, History/rollback and Stop tracking - which left that entire half of the app with no keyboard path at all. ## [0.2.10] - 2026-09-14

### Fixed

- GitCloud does not work with files in **group folders, received shares or external storages**, and until now it failed in a confusing way rather than a clear one: the commit came back with a raw git error, `Failed to stage files: fatal: pathspec 'Team Folder/report.md' did not match any files`. Nothing was staged or recorded (no corruption), but nothing explained why either. Worse, folder recursion crossed mount boundaries, so committing an ordinary home folder that merely *contained* a group folder or a received share failed the **entire** commit, legitimate local files included. GitCloud keeps its existing home-folder-only scope; it now says so clearly and early instead of leaking git's pathspec error.
  - Root cause is that `isLocal()` is the wrong predicate. The working tree is derived exclusively from the **home** storage - `VcsService::resolveRepositoryPath()` returns `$userFolder->getStorage()->getLocalFile(...)` - while every file is addressed by `$userFolder->getRelativePath($node->getPath())`, a *virtual* mount-tree path (`lib/private/Files/Utils/PathHelper.php:18-29` is pure string subtraction and happily crosses mount boundaries). A group folder is a separate mount *inside* `files/` whose bytes live at `<datadirectory>/__groupfolders/<numericId>/...` (confirmed from core: `lib/private/Files/Cache/Propagator.php:55-63`, `lib/private/Files/Cache/LocalRootScanner.php:53`, `lib/private/User/Manager.php:832`), so `Team Folder/report.md` is not a real path under the work tree - and no string transformation recovers the on-disk one, which contains the numeric id, not the folder name. The existing guard rejected only `!isLocal()` (`ApiController::collectRelativeFilePaths`), but `Wrapper::isLocal()` just delegates down the chain (`lib/private/Files/Storage/Wrapper/Wrapper.php:269`) to `Local::isLocal() === true` (`Local.php:554`): it means "the bytes are on this filesystem", **not** "the bytes are in this user's home". Group folders sailed past it, and so did received shares of local files and local external storages.
  - The new predicate is a storage-identity comparison, `$node->getStorage()->getId() === $userFolder->getStorage()->getId()`, in a new shared `Service\WorkingTree::contains()` helper (static and non-injected, following the existing `GitArchitecture::detect()`/`BundledGitBinary` convention - and deliberately not a `VcsService` method, since `VcsService` is mocked throughout the controller and listener test suites where an instance method would silently default to `false`). It aligns exactly with how `resolveRepositoryPath()` derives the work tree, so one check covers group folders (`local::<datadir>` via `Jail`→`LocalRootStorage`), received shares and external mounts, plus any future mount type. Chosen over `instanceOfStorage(IHomeStorage::class)`, which works only because `SharedStorage` carries an explicit special case returning `false` for it (`apps/files_sharing/lib/SharedStorage.php:220-228`); over comparing resolved local paths, since `Local::getSourcePath()` runs `realpath()` when `localstorage.allowsymlinks` is off (`lib/private/Files/Storage/Local.php:521+`), so string equality isn't guaranteed; and over `getMountPoint()`, which has no declared return type (`lib/public/Files/FileInfo.php:231`) and so returns `null` from every existing node mock.
  - `collectRelativeFilePaths()` now throws a new `Exception\NotInWorkingTreeException` (mirroring the existing `NotLocalStorageException`) when the check fails, and `commitChanges()` turns it into a 400 naming the offending path: "GitCloud can only track files in your personal files - group folders, shared folders and external storages are not supported: `<path>`". The `isLocal()` check is kept **first**, so a *remote* external storage keeps its existing, more specific message. `rollbackSnapshot()` gained the same guard next to its own `isLocal()` check so the two stay consistent. The all-or-nothing behavior during folder recursion is deliberate: it matches the convention established for `NotLocalStorageException` in 0.1.17, and the message names the path responsible rather than silently under-committing.
  - `findUncommittedFiles()` now skips children on another storage, so a file that can never be committed no longer surfaces as `Uncommitted` in Directory Detail.
  - `GitTrackedNodeRenamedListener` had the same root cause with a different symptom: moving a tracked home file *into* a group folder made `autoCommitRename` stage an old path that no longer exists plus a new path that never will, so `git add` failed, the listener logged a warning, and GitCloud's state went stale. When the rename target is outside the working tree it now records the move as a deletion instead (the existing `VcsService::autoCommitDelete`) - from GitCloud's perspective the file has left its world, which is exactly what `Deleted` already means, and it keeps History/Rollback reachable.
  - Frontend: the Files-app "Add to GitCloud" action's `enabled()` was a stub returning `true`; it now hides the action on any node carrying a non-empty `nc:mount-type`. That property is in `@nextcloud/files`' default PROPFIND set and is computed per node from its mount point (`apps/dav/lib/Connector/Sabre/FilesPlugin.php:405-407`), so it is populated for every descendant of a mount rather than just the mount root, and is `''` for the plain home mount (`lib/private/Files/Mount/MountPoint.php:280-282`). Treating *any* non-empty value as "hide" is what keeps it future-proof - deliberately not matching the literal string `'group'`, which can't be verified in this checkout. The backend check stays authoritative: a home folder containing a nested mount still passes the frontend test.

Actual group folder support (a per-group-folder repository with shared history) is a separate, much larger piece of work, now tracked as its own Phase 3 roadmap item.

Covered by 6 new tests: `WorkingTreeTest` (same storage id → true, differing → false), 3 `ApiTest` cases (a commit of a file on a group-folder storage is rejected with the new message; a nested different-storage child inside a committed home folder is likewise rejected - modelled the way `testCommitChangesFailsWhenFolderContainsNestedNonLocalMount` models an external mount, but with `isLocal()` returning **true** and a differing `getId()`; `findUncommittedFiles` skips such a child), and a `GitTrackedNodeRenamedListenerTest` case asserting a move outside the working tree calls `autoCommitDelete` and never `autoCommitRename`. Full PHPUnit suite **163 tests, 388 assertions** (up from 157/375) verified passing inside the running `stable34` container (synced via `docker cp` + a restart first). One pre-existing test needed a one-line change: `testHandleAutoCommitsRenameForTrackedFile` now stubs `getStorage()` on its target node and user folder, because `Node::getStorage()`/`FileInfo::getStorage()` have no declared return type in Nextcloud 34 (`lib/public/Files/Node.php:76`), so an unstubbed mock returns `null` - the storage-identity choice avoided churn everywhere else, including all of `ApiTest`, which already hands the user folder and its nodes the same `IStorage` mock. `composer lint`, `composer cs:check`, `npm run lint`, `npm run stylelint` and a clean `vite build` all verified (only the pre-existing, known-benign `v-html` warnings remain). `composer openapi` was not re-run: no route or response *shape* changed, only message text.

## [0.2.8] - 2026-09-12

### Changed

- **GitCloud's Git repository no longer lives inside the user's files.** It used to sit at `files/.git`, i.e. at the root of the user's own Nextcloud storage, which is what made it visible as an ordinary folder in the Files app, WebDAV, mobile apps and non-official sync clients in the first place - and what forced 0.2.6/0.2.7's three guards (delete, rename, write) to exist at all. It now sits at `<data>/<user>/gitcloud`, a *sibling* of `files` rather than a child, alongside core's own per-user directories (`files_trashbin`, `files_versions`, `uploads`, `cache`). Nextcloud only ever exposes `files/` as a user's storage, so the repository is now simply not reachable through the Files app, WebDAV or any sync client: there is nothing to browse into, nothing to accidentally drag a file into, and nothing to delete, rename or overwrite. Chosen over the alternative of merely improving the blocked-write error message, since it removes the exposure instead of reporting it better.
  - `VcsService` gained `resolveGitDirectory()` (the new location, derived from the working-tree path so it follows whatever home storage a user actually has, rather than being reconstructed from a configured data directory), a private `hasRepository()` replacing the eight scattered `is_dir($repositoryPath . '/.git')` checks, and a private `gitLocationArgs()` that prepends `--git-dir=`/`--work-tree=` to every invocation in `runGit`/`runGitConfigGet`/`runGitConfigSet`. `gitLocationArgs()` returns nothing when the path has no repository beside it - notably for the `/` used to read *system-wide* identity config - so that call keeps behaving exactly as before. Pointing the two config helpers at the repository matters as much as `runGit` itself: without it, GitCloud's identity check would silently read, and `runGitConfigSet` silently write, the server-wide git config instead of this user's repository.
  - `ensureRepository()` initializes with `--git-dir` **only**. Adding `--work-tree` to `git init` produces an incomplete repository - no `HEAD`, no `objects/` - verified empirically against git 2.55.0 rather than assumed; every later command supplies both flags, which is what actually binds repository to working tree. Since initializing that way leaves `core.bare = true`, it is cleared immediately afterwards so a freshly created repository is identical to a relocated one.
  - `deleteHistory()` and `createHistoryBackup()` follow the new location. The backup tarball's top-level entry is consequently `gitcloud/` rather than `.git/`, matching where it now has to be restored to.
- A one-time repair step, `Migration\MoveGitDirectoryOutOfUserFiles` (registered as a `<post-migration>` step in `info.xml`, this app's first use of `OCP\Migration\IRepairStep`), relocates existing installs on `occ upgrade`. It moves the repository with a single `rename()` - verified that a plain repository whose `.git` directory is moved to a sibling path keeps its full history and works unchanged under `--git-dir`/`--work-tree`, so no git-level surgery is needed - and then drops the now-stale `.git` row from `oc_filecache` via the same `IUpdater` the app already uses after writing content outside the Node API (0.1.14), so it doesn't linger as a phantom folder in the Files app. Working-tree files are never touched. If a repository somehow already exists at *both* locations it leaves both alone and warns, rather than guessing which holds the history the user wants; a user on non-local storage (where GitCloud never created a repository) is skipped.
- The `.git` delete/rename/write guards from 0.2.6/0.2.7 are deliberately kept. They are now belt-and-braces rather than the only line of defense, and still protect anyone who has a `.git` directory in their files for unrelated reasons.

## [0.2.7] - 2026-09-12

### Fixed

- 0.2.6's `GitRepositoryWriteGuard` now also blocks a write made through the Files web app's own browser-session-authenticated upload (drag-and-drop, "New > Upload file", including its overwrite/conflict-resolution flow) - the gap shipped as a "Known limitation" in 0.2.6. Root-caused this session by reading Nextcloud 34's actual source rather than guessing:
  - `remote.php` (the entry point for every `/remote.php/dav/...` request) never calls an unfiltered `IAppManager::loadApps()`. It only calls `loadApps(['authentication'])`, `loadApps(['extended_authentication'])`, `loadApps(['filesystem', 'logging'])`, then `loadApp('dav')` specifically (`remote.php:126-130`). GitCloud declared no `<types>` in `appinfo/info.xml`, so `AppManager::isType()` returned false for all of those filtered calls and GitCloud was never loaded - meaning `Application::register()`/`boot()`, and therefore the `OCP\Util::connectHook()` call that registers the write guard, never ran for a DAV request through this path alone.
  - It nonetheless ran for `curl`/sync-client writes because `apps/dav/lib/Connector/Sabre/Auth.php::auth()` has two branches: an **already-logged-in-via-cookie fast path** (`$this->userSession->isLoggedIn() && ...`) that returns immediately without further app loading, and a **fresh-credential path** (`parent::check()` -> Sabre's `AbstractBasic` -> `validateUserPass()` -> `IUserSession::logClientIn()`) that performs a full login and ends up loading the full app set. A browser that already holds a session cookie always takes the fast path for every DAV request in that session; `curl -u admin:admin` and the desktop sync client have no cookie, so every one of their requests takes the fresh-login path. That explains every observation from last session exactly - browsers not blocked, `curl`/sync client blocked, regardless of target path, and regardless of whether the target was `.git` or an ordinary tracked file.
  - The fix is an `appinfo/info.xml` change only: GitCloud now declares `<types><filesystem/></types>`. Since `remote.php` calls `loadApps(['filesystem', 'logging'])` unconditionally, **before** the Sabre Auth plugin even runs, on every DAV request regardless of which auth branch is taken afterwards, marking GitCloud as a `filesystem`-type app guarantees `Application::register()`/`boot()` runs for every DAV request and closes the gap for both auth paths. This is a standard, documented Nextcloud mechanism (`IAppManager::loadApps()`/`isType()`, backed by an app-config `types` value populated from `info.xml` by `AppManager::setAppTypes()` from within `upgradeApp()`), not private API and not a workaround - and it is semantically accurate, since GitCloud is fundamentally a filesystem-hooking app. The only behavioral side effect (per `AppManager::hasProtectedAppType()`) is that a `filesystem`-typed app cannot be restricted to specific groups, which GitCloud never supported anyway. Because the cached `types` value is only refreshed on an app version bump, this necessarily ships as a version bump rather than a silent edit.
- No PHP or JavaScript changed - `GitRepositoryWriteGuard`, `Application::boot()`, and the delete/rename listeners were already correct; they simply were never reached for this one request pattern.

### Known limitation

- Nextcloud core turns a hook-cancelled write into a generic `Sabre\DAV\Exception` ("Could not write to final file, canceled by hook", `apps/dav/lib/Connector/Sabre/File.php:149`), which Sabre maps to **HTTP 500**, not a 403. The Files app's uploader treats a 500 as a transient server error and retries the PUT with exponential backoff rather than reporting "not allowed" - observed live as 6 retries over ~170 seconds with the upload bar still showing a (growing) "N seconds left" estimate and no error toast in that window, rather than an immediate, clear permission message. The write itself never reaches disk either way, which is what matters for `.git` integrity, and this is core's own mapping rather than something GitCloud sets - left as-is rather than reaching for a different, less-documented cancellation mechanism purely for the error text.

## [0.1.23] - 2026-08-25

### Added

- GitCloud now reacts to a tracked file being deleted, renamed, or moved outside of GitCloud (Files app, WebDAV, sync clients, `occ`, ...) instead of silently losing track of it. Two new server-side event listeners, `GitTrackedNodeDeletedListener` and `GitTrackedNodeRenamedListener` (registered in `lib/AppInfo/Application.php` on Nextcloud's `NodeDeletedEvent`/`NodeRenamedEvent` — the same event covers both a same-directory rename and a cross-directory move, there is no separate move event), immediately auto-commit the change to the file owner's GitCloud repository: a delete stages the removal (`VcsService::autoCommitDelete`, "Auto-commit: deleted \<path\>"), a rename/move stages both the old and new paths together so git's own similarity detection records it as a rename (`VcsService::autoCommitRename`, "Auto-commit: renamed \<old\> to \<new\>"). ### Known limitation

- Snapshot rows created before this release have no `file_id` (it can't be backfilled retroactively — there's no reliable way to map an old path string to a fileid after the fact, especially for a file already deleted). A delete/rename of a file whose only history predates this migration silently no-ops (today's pre-0.1.23 behavior: the change is simply invisible to GitCloud) until the user commits that file again post-upgrade, after which its fresh fileid-carrying snapshot row makes future renames/deletes on it link correctly.
