# GitCloud Development Roadmap

This document tracks GitCloud's phase-by-phase development history and future plans. See [README.md](README.md) for what the app does and how to install/use it, and [CHANGELOG.md](CHANGELOG.md) for a per-release account of every change.

We tackle this project in progressive phases to ensure stability and testability at each step.

## ✅ Phase 1: Foundation — Complete

**Goal:** Establish the app structure, UI entry points, and baseline interface. Everything below is done.
- ✅ Main dashboard view — shows aggregate statistics (file count, total size, Git status indicators).
- ✅ Right-click context menu entry "Add to GitCloud" registered via `@nextcloud/files`.
- ✅ Wire the backend stub (`VcsService`) to actually stage and commit selected files when the context action is triggered.

## ✅ Phase 2: Core Actions — Commits & Rollbacks — Complete

**Goal:** Reliable, everyday Git operations that users need most.
1. ✅ **Wire up the dashboard UI** — Connect the dashboard's placeholder elements to real, live data (file counts, sizes, Git status) instead of dummy values.
   - ✅ **Follow-up:** Redesign the dashboard into a two-state layout — an Overview (global stats + a searchable list of committed directories) that switches to a Directory Detail view (stats scoped to the selected directory, plus Commit/Rollback controls) when a directory is selected, with a way to deselect back to Overview. Commit Changes and Rollback Snapshot are both wired to their real endpoints.
   - ✅ **Follow-up:** Replace the mock-derived committed-directories list and Directory Detail file set with real data — `GET /apps/gitcloud/directories` groups every file the user has ever committed (from `gitcloud_snapshots`) by directory. The directory-scoped stats numbers (file count is now accurate; total size and Git status still reflect the whole repository, not just the selected directory) remain a follow-up — see kanban.
   - ✅ **Follow-up:** Directory Detail's total size and Git status are now scoped to the selected directory instead of the whole repository — `GET /apps/gitcloud/status` accepts an optional `directory` param backed by a new `VcsService::getDirectoryStatus`.
2. ✅ **Create a database** — Add persistent storage (Nextcloud app database table(s) via migrations) to track snapshot/commit metadata.
3. ✅ **Commit Changes** — Collect a user-provided commit message in the UI and record a snapshot row for each commit (the underlying `git add`/`git commit` plumbing and context menu wiring were already completed in Phase 1).
4. ✅ **Rollback Snapshot** — Expose available snapshots per file via the API, revert selected files to a previously captured snapshot, and record a new snapshot row for the rollback. The dashboard's Rollback Snapshot button prompts for which file (when the selected directory has more than one real committed file) and which snapshot to restore, following the same `window.prompt`/`window.alert` convention as the commit flow.
   - ✅ **Follow-up:** Redesigned Commit/Rollback around real `@nextcloud/vue` UI instead of `window.prompt`/`alert`/`confirm` — commit is now per-file (checkbox selection + a shared `CommitDialog` used by both the dashboard and the Files-app right-click action) and rollback is a per-file `RollbackPanel` snapshot timeline with a confirm step, replacing the old prompt-chain flow. The dashboard also dropped its light-theme lock and now follows the instance's active theme. Per-file Modified/Unchanged status was considered but left out — no backend field exists for it yet; see kanban.
   - ✅ **Follow-up:** Added a real per-file Modified/Unchanged status to `GET /apps/gitcloud/directories` (`VcsService::getFileStatuses`, backed by `git status --porcelain` scoped to each directory's files) and surfaced it in Directory Detail's file list, plus an "N modified" pill on Overview's Committed Directories list. This was the last open item for Phase 2.
   - ✅ **Follow-up:** The per-file status set was later expanded beyond Modified/Unchanged to include `Uncommitted` (a file physically present in an already-tracked folder that's never been committed) and `Deleted` (a committed file removed outside GitCloud), with matching pills/tags in the UI. See CHANGELOG 0.1.21 and 0.1.23.

## 🔧 Phase 3: Gaps & Fixes (Active)

**Goal:** Close the *gaps* — things that should already work but don't, plus small, self-contained fixes. Genuinely new capabilities live in Phase 4 instead, so this phase stays short and shippable. All Phase 3 prerequisites (verifying prior-phase work holds up in the real running instance) are cleared — see the Phase 3 kanban.

**Open — logged by the 2026-09-15 deep review** (second full pass: whole project re-read, plus the running `stable34` instance driven over its real OCS/WebDAV endpoints; every bug below was reproduced live). Full repro steps, affected file:line and suggested fixes are on the Phase 3 kanban.

Bugs 10, 11, 12 and 14 share one amplifier: `VcsService::commitChanges` treats "git has nothing staged" as a hard error and returns *before* recording a snapshot row, so anything that leaves content in git without a matching row strands the file as permanently `Uncommitted`.

- ⚠️ **`#GC-Phase3-Bug-10` (data loss): a filename containing a git pathspec glob character silently commits and rolls back other files.** Paths are passed to git as bare pathspecs after `--`, which stops option parsing but not globbing. Committing a real file named `report-*.txt` also committed `report-private.txt` and `report-public.txt`; rolling it back silently overwrote both files' newer, uncommitted content on disk. `*`, `?`, `[`, `]` are all legal Nextcloud filenames.
- ⚠️ **`#GC-Phase3-Bug-11`: "Stop tracking" is one-way** — after untracking a file, committing it again fails forever with "No changes to commit for the selected file(s)" and it is stuck as `Uncommitted`. An ordinary user flow; makes the 0.2.3 Stop-tracking feature non-reversible.
- ⚠️ **`#GC-Phase3-Bug-12`: concurrent commits collide on git's `index.lock`.** Six parallel commits: only 2 of 6 succeeded; the rest leaked raw git errors, one of them dumping the user's entire untracked-file listing into the API response. Reachable whenever a sync client or the auto-commit listeners fire alongside a user action. There is no locking anywhere in the codebase.
- ⚠️ **`#GC-Phase3-Bug-13` (data loss): `deleteHistory` reports success after a partial wipe**, leaving a half-deleted repository (`objects/`/`refs/` emptied, `HEAD`/`config`/`index` surviving) that `ensureRepository()` never reinitialises because `is_dir()` still passes. Snapshot rows are deleted anyway, and every later commit fails with `error: Error building trees`. Same unchecked-return-value defect as the already-fixed `#GC-Phase3-Bug-5`, in a sibling method.
- ⚠️ **`#GC-Phase3-Bug-14`: a commit message over 4000 characters returns HTTP 500** (`SQLSTATE[22001] Data too long`) after git has already committed, stranding the file per the shared amplifier above. No length validation exists at the API boundary; the DB column is 4000 chars.
- **`#GC-Phase3-Bug-15`: a `..` path segment in any path parameter returns HTTP 500 instead of 400.** `InvalidPathException` is uncaught in `/commit`, `/snapshots` and `/rollback`. No security impact — core blocks the traversal and nothing reaches git — but it logs an exception and returns an unhelpful OCS 996.
- **`#GC-Phase3-Bug-16` (accessibility): the committed-directories list is unreachable by keyboard.** Each row is a bare `<li @click>` with no `role`, `tabindex` or key handler, and selecting a directory is the only route to commit, History/rollback and Stop tracking — so the whole Directory Detail half of the app has no keyboard path. The shipped bundle contains zero `onKeydown` and zero `role=`.
- **`#GC-Phase3-Bug-17` (accessibility): the per-file commit checkbox has no accessible name** — the app's only raw `<input type="checkbox">`, with no label, `aria-label` or `aria-labelledby`.
- **`#GC-Phase3-Bug-18` (accessibility): the History drawer is a hand-rolled modal** with no `role="dialog"`, focus trap, initial/restored focus, or Escape handler, while covering the page at `z-index: 2000`.
- **`#GC-Phase3-Bug-19` (accessibility): no status or error banner is a live region** (zero `aria-live` in the bundle), decorative icons aren't `aria-hidden`, and Directory Detail has no `<h1>`.
- **`#GC-Phase3-Bug-20`: the admin Git-binary panel silently vanishes** when its status request fails — an empty `catch` sets `gitStatus = null` and every control in the section is `v-if`-gated on it.
- **`#GC-Phase3-Maint-2`: maintenance sweep** — duplication (folder-descendant resolution copy-pasted across all three auto-commit listeners; `runProcess()` duplicated across two services; the static-git download/install sequence implemented twice; five copies of the confirm-dialog button array), dead/inert code, and tooling gaps (`nextcloud/ocp` pinned to `dev-stable31` while the app targets NC 34; **no CI workflow runs PHPUnit**; the two `.js` frontend files are excluded from type checking).

**Done**
- ✅ ~~Git binary not installed error message~~ — done in 0.2.1, see the note in README's Requirements section.
- ✅ ~~Surface real git error output instead of a generic failure message~~ — done in 0.2.2.
- ✅ ~~Remove specific files / folders from GitCloud (stop tracking a file without deleting it from disk)~~ — done in 0.2.3.
- ✅ ~~Integrate static git into GitCloud~~ — done in 0.2.4/0.2.5, **verified end-to-end against a real running instance**. `VcsService` resolves which `git` executable to invoke according to an admin-configured mode (**Settings > Administration > GitCloud**, default **Automatic**): prefer a bundled, statically-linked `git` binary (linux/amd64 or linux/arm64, matching the server's architecture) at `bin/<arch>/git` when present, falling back to a system-installed `git` on `PATH` when it isn't; **System git** and **Static git** modes pin to one or the other explicitly, the latter with no PATH fallback. The binary can be fetched either by an explicit `composer fetch-git-static` step (`build/fetch-git-static.php` + the pinned version/checksums in `build/git-static.json`) or, since 0.2.5, with a "Download static git" button directly on that settings page (`GitStaticBinaryService`) — both download and sha256-verify releases from the companion [`gitcloud-git-static`](https://github.com/zschaub/gitcloud-git-static) project rather than committing the binary to this repo, and both record which exact version they installed (`bin/<arch>/git.version`) so the settings page's "Check for updates" button can tell whether the currently-installed build is older than what this version of GitCloud has pinned (a purely local comparison, not a live check against GitHub) and offer to update it via the same trusted download-and-verify flow. Chiefly needed for Nextcloud AIO, whose container filesystem is replaced on every update, and eventually a no-shell-access App Store install.
- ✅ ~~Fail fast on files outside the user's personal files~~ — done in 0.2.10. Group folders, received shares and external storages are rejected up front with a clear message naming the offending path, instead of failing with a raw git pathspec error. Actually *supporting* them is a Phase 4 item.
- ✅ ~~`#GC-Phase3-Bug-1`: Snapshot history ordered non-deterministically~~ — done in 0.2.11. `SnapshotMapper` ordered only by `created_at`, which is whole seconds, so two snapshots recorded for the same file in the same second had no defined order — observed live as the rollback panel labelling an older snapshot "Current version" while the newest was offered as a rollback target, with the same wrong row also feeding the auto-commit listeners' "latest snapshot" gate and the dashboard's Deleted pill. `findAllForUserUnderPath` already broke ties with `addOrderBy('id', 'DESC')` (added in 0.1.25 for its own purposes); the same tiebreaker is now added to the three sibling methods that were missing it — `findAllForUser`, `findAllForFile`, and `findLatestForFileId` — since the auto-increment `id` is guaranteed to follow insertion order. Verified against the real running instance by forcing two real snapshot rows to an identical `created_at` directly in the database and confirming both the snapshot list and the auto-commit parent-chaining endpoint still resolved the newer row correctly.
- ✅ ~~`#GC-Phase3-Bug-2`: Renaming/moving or trash-restoring a tracked folder silently lost tracking of its files~~ — done in 0.2.11. The rename and restore listeners only reacted when the event's own node had GitCloud history, which a folder never does; the delete listener got a folder fallback in 0.1.25 (treat the node's own path as a possible folder prefix and look up tracked descendants from snapshot history), but the other two never did. Both listeners now mirror that exact fallback: a rename computes each descendant's new path by substituting the old folder prefix for the new one, and a restore restores only descendants whose latest status is actually `deleted`. Verified end-to-end against the real running instance: a real WebDAV folder move correctly carried both files' history to their new path (previously they vanished from the dashboard entirely), and restoring the same folder from the trash via a real DAV trashbin restore correctly cleared both files' `Deleted` status with their content intact on disk (previously they stayed `Deleted` forever).
- ✅ ~~`#GC-Phase3-Bug-5`: A failed static-git install still reported success~~ — done in 0.2.11. `GitStaticBinaryService`'s install path never checked the return values of its own `copy()`/`chmod()`/`file_put_contents()` calls, so a write failure (e.g. a read-only app directory) was silently ignored and the method still reported success. All three are now checked, returning a clear failure immediately, matching every other failure branch already in the method. Verified with a new test that `chmod`s the target directory read-only and confirms both failure is reported and nothing is left on disk - genuinely exercised by running the full suite as the unprivileged `www-data` user (root ignores permission bits and would make the test meaningless).
- ✅ ~~`#GC-Phase3-Bug-6`: "Static git is already up to date" shown even when the installed version is unknown~~ — done in 0.2.11. The backend already distinguished "unknown version" (`installedVersion: null`) from "genuinely up to date" in its response data; the frontend note card just never branched on it, showing the same "up to date" text for both. Split into two note cards keyed on `installedVersion`, and the "Download static git" button now also reappears when the installed version is unknown, so the new message's suggested fix is actually reachable. Verified against the real running instance's live static-git status endpoint by temporarily clearing its real version marker and confirming the response payload matches the new template branch, then restoring it.
- ✅ ~~`#GC-Phase3-Bug-3`: Files-app commit dialog rendered unstyled~~ — done in 0.2.11. The app registered the Files-app script but never the matching stylesheet; the CSS was already built, just never enqueued. One-line `Util::addStyle()` fix, confirmed live: the Files app page now links the stylesheet alongside the script.
- ✅ ~~`#GC-Phase3-Bug-4`: Dashboard only filled about half the content area~~ — done in 0.2.11. `NcAppContent` was mounted with no `NcContent` ancestor, the component that actually supplies the sizing context it needs. Wrapped the dashboard's template root in `NcContent` (no `NcAppNavigation` needed — GitCloud has no sidebar). Not re-measured in a real browser this session (no browser-automation tool available) — the user should confirm the dashboard now matches the Files app's content width.
- ✅ ~~`#GC-Phase3-Bug-7`: Untracking the last file in a directory gave no feedback~~ — done in 0.2.11. The success/error banner lived only in the Directory Detail view, but untracking a directory's last file navigates back to Overview in the same action — moved the banner to a location rendered in both views.

## 🔮 Phase 4: New Features (Exploratory)

**Goal:** Genuinely new capabilities, once the Phase 3 gaps are closed. Everything here is a *candidate* — scope, and whether an item is worth doing at all, gets decided when it's picked up.

- **Shared / group folder support** — 🔍 *to be explored; may not be feasible in this form.* GitCloud is home-storage-only: the working tree is `<data>/<user>/files`, with one repository per user at the sibling `<data>/<user>/gitcloud`. A group folder is a separate mount inside `files/` whose bytes live at `<data>/__groupfolders/<id>/` and are shared by many users, so it can't be folded into any single user's repository — supporting it means a repository *per group folder*, with history shared across every member, plus answers to who may roll back whose commits and how the dashboard presents a repository the user doesn't solely own. Received shares and external storages are the same shape of problem. As of 0.2.10 GitCloud at least fails fast and clearly on all three (see Phase 3); this item is the actual feature.
- **Compare snapshots** — view a diff between two historical snapshots of a file.
- **Manage branches visually.**
- **Delete commits** — a targeted removal of individual commits from history, distinct from the existing Personal Settings option to wipe a user's *entire* GitCloud history at once.
- **Multi-file / whole-directory rollback to a single point in time** — rollback is currently per-file only; restoring several files together to how they looked at a given moment was deliberately scoped out of the original rollback implementation.
- **Diff/preview view** — show what actually changed before committing or before rolling back; both actions are currently "blind," with no content diff shown anywhere in the UI.
- **Ignore-pattern / exclusion support for auto-tracking** — once a folder has any committed file, every subsequent change to any file in it is auto-committed, with no way to exclude specific paths or file types.
- **Snapshot pruning/retention controls** — Personal Settings currently only offers a full history wipe; a middle ground (e.g. "prune snapshots older than X" or "keep the last N per file") would help reclaim space without losing everything.

*This phase is tentative — we will refine the feature list based on what users actually need.*
